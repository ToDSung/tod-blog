## 5. Missing-risk scan (up to 3, per task instructions — see also §4.3 which is the strongest one)

1. **ESLint type-aware parsing of Storybook/config files outside tsconfig `include`** (detailed in §4.3 above, spec.md:62 / eslint.config.mjs:20-23). This is the single most concrete, repo-grounded risk found: it already happened once (Phase 0 fixed an identical bug for `jest.config.ts` and `**/*.spec.ts`/`**/*.test.ts`), the plan explicitly cites "比照 leetcode 模式" (follow the leetcode pattern) as its template for `packages/ui/eslint.config.mjs` (plan.md:26), yet doesn't carry forward the specific carve-out that made the leetcode pattern work. Because `npx eslint .` clean is both spec §8's *first* acceptance line and a stated "驗證底線" (validation baseline) for every single phase (plan.md:11), this failure would block every Phase-1.3-onward commit under the repo's own pre-commit lint-staged hook, not just fail a final audit.

2. **Windows/PowerShell tooling gaps for prose-only acceptance criteria.** AGENTS.md:60-66 documents this machine has no `&&`/`||`, no native Unix `find`/`grep`/`sed`, UTF-16 LE default file writes, and a hard "stop after two failed retries" rule. Several plan.md acceptance criteria assume some unspecified inspection tooling exists (bundle-content checks in Phase 3.2, plan.md:50; visual "smoothness" in Phase 5.2, plan.md:70) without naming a concrete command. A cold-start sonnet/opus executor on this Windows box, given only the acceptance text (per model-dispatch's "reviewer only gets acceptance criteria + output location" review protocol, plan.md:10), has no specified path to a mechanically reproducible check and is likely to either invent brittle tooling or silently downgrade the check to eyeballing — both of which defeat the plan's own stated goal of "機械可查" (mechanically checkable) acceptance (plan.md:9).

3. **Husky pre-commit hook amplifies risk #1 across every phase.** `.husky/pre-commit:1` runs `npx lint-staged` unconditionally before the leetcode-specific test logic; `.lintstagedrc.json:2` runs `eslint --fix` on every staged `*.{ts,js,tsx,jsx}` file with no package exclusion. Combined with risk #1 (Storybook config files falling outside type-aware parsing scope), and plan.md's own rule that "每個 Phase 至少一個 commit" (plan.md:12), the *entire* multi-week execution plan is exposed to the same commit-blocking failure mode being written into the very first Phase-1.3 commit that introduces `.storybook/`, since husky's hook is not bypassable per AGENTS.md ("不可 `--no-verify`", plan.md:12) without explicit owner approval.
