# UI Tooling Research for `packages/ui`

Researched 2026-07-13 against primary/official sources (npm registry API, storybook.js.org, ui.shadcn.com, zod.dev, tanstack.com, shiki.style, GitHub repos) for a planned `packages/ui` shared component library: shadcn/ui + Tailwind v4 + motion + React 19, in the `tod-blog` pnpm monorepo (which also contains `packages/tod-blog`, a Next.js 15 App Router app using `output: 'export'` static export — no server runtime, no server actions).

## 1. TL;DR

- **Storybook 10.5.0** (npm registry, current), framework package **`@storybook/react-vite`** (not `@storybook/nextjs-vite`, which is Next.js-specific) — React 19 is a supported peer (`^16.8.0 || ^17 || ^18 || ^19`) since the 9.0 React 19 investigation closed. Live **inside `packages/ui`** — no official Storybook guidance recommends a separate sibling "storybook" package for a single component library.
- Forms: **`react-hook-form@7.81.0` + `zod@4.4.3` + `@hookform/resolvers@5.4.0`**. shadcn/ui's newest primitive is **`Field`** (composable, form-library-agnostic, Oct 2025+) used with RHF's `<Controller>`, superseding the old `<Form>` wrapper — and as of July 2026 shadcn defaults new projects to **Base UI** (Radix opt-in via `-b radix`): https://ui.shadcn.com/docs/changelog
- **`@tanstack/react-query@5.101.2`**, peer dep `react: "^18 || ^19"` per npm registry — explicit React 19 support. Pattern: `<form onSubmit={handleSubmit(mutate)}>` (RHF validates, `useMutation` submits) per TanStack Query maintainer guidance: https://tkdodo.eu/blog/react-query-and-forms
- Markdown (scope: **GFM + syntax highlighting + copy button only**; KaTeX/mermaid deferred): **`react-markdown@10` + `remark-gfm`** rendered via its client-side **`MarkdownHooks`** component so the async **`@shikijs/rehype`**/Shiki (fine-grained JS-engine bundle) plugin works in a client component — not `next-mdx-remote` (server-side `serialize()`, incompatible with static export) or MDX runtime compile (RCE risk on arbitrary strings).
- Styling: `@tailwindcss/typography@0.5.20` officially supports Tailwind v4 (peer `>=4.0.0`), and shadcn's new **`typeset`** system (July 2026) is a first-party alternative purpose-built for rendered markdown; shadcn/ui has **`input-otp`** and `Field`/`Input Group` built-in, but code-block-copy-button, heading anchors (`rehype-slug` + `rehype-autolink-headings` off the shelf), callouts, and password-visibility-toggle are assembled, not shipped.

## 3. Storybook placement recommendation

**Recommendation: put Storybook inside `packages/ui`**, as `packages/ui/.storybook/` + stories colocated with components, not as a separate sibling package.

Reasoning and citations:

- Storybook's own framework docs describe `@storybook/react-vite` as the correct framework for "React applications built with Vite" in general — i.e., no separate app shell is required, it works directly against a component package. https://storybook.js.org/docs/get-started/frameworks/react-vite
- `@storybook/nextjs-vite` is explicitly scoped to Next.js apps ("We recommend using `@storybook/nextjs-vite` for most Next.js projects") and pulls in Next-specific integrations (next/image, next/font, routing, RSC) that a standalone `packages/ui` library does not need and should not depend on. https://storybook.js.org/docs/get-started/frameworks/nextjs
- I could not find first-party Storybook documentation (storybook.js.org) that prescribes a dedicated sibling "storybook" workspace package as the standard monorepo pattern. The closest official-adjacent material is Storybook's own GitHub discussions (community RFC and support threads, not shipped docs), which describe root-level or per-package Storybook setups and Composition for combining multiple storybooks — none of these mandate a separate package for a single component library. https://github.com/storybookjs/storybook/discussions/22521 ; https://github.com/storybookjs/storybook/discussions/11351
- Given there is only one UI package in this monorepo (no competing app-level Storybooks to compose), colocating Storybook config and stories inside `packages/ui` is the simplest setup consistent with Storybook's own single-project quick-start instructions, and avoids an extra workspace package whose only content is Storybook plumbing.
- Caveat: one secondary/community source (a Medium write-up surfaced via search, not storybook.js.org) argued against putting Storybook inside a UI library package to preserve an app/library boundary. This is not an official position and conflicts with the simpler colocated approach above; flagging it rather than treating it as authoritative. https://medium.com/@awesome-jeremy/storybook-setup-for-mono-repo-multi-package-structure-component-library-8bf915d7e4d8

## 4. Forms + Query pattern (client-side login/register, static export)

Because `packages/tod-blog` uses `output: 'export'` (no server runtime, no server actions, no RSC data mutations), all auth flows must run entirely client-side against an external API. The composition pattern, based on the primary sources below:

1. **Schema-first validation**: define a `zod` schema for the form (`z.object({ email: z.string().email(), password: z.string().min(8) })`), per shadcn/ui's documented RHF integration. https://ui.shadcn.com/docs/forms/react-hook-form
2. **Form state**: `useForm({ resolver: zodResolver(schema) })` from `react-hook-form`, wiring `zodResolver` from `@hookform/resolvers/zod`. This is shadcn's own documented pattern (`useForm` + `<Controller>` + `Field`/`FieldLabel`/`FieldError` primitives, with `data-invalid`/`aria-invalid` for accessibility). https://ui.shadcn.com/docs/forms/react-hook-form ; https://ui.shadcn.com/docs/components/field
3. **Field layout**: shadcn's newer `Field` component family (`Field`, `FieldLabel`, `FieldDescription`, `FieldError`, `FieldGroup`, `FieldSet`/`FieldLegend`) is form-library-agnostic — `FieldError` accepts either an RHF `errors` array or any Standard-Schema validator's issues (Zod included), so it composes directly with the RHF+Zod stack without shadcn's older RHF-only `<Form>` wrapper. https://ui.shadcn.com/docs/components/field ; https://github.com/shadcn-ui/ui/discussions/9505
4. **Submission → mutation**: TanStack Query's documented `useMutation` pattern is generic — an `onSubmit` handler that calls `event.preventDefault()` and then `mutation.mutate(data)` — TanStack's own mutations guide does not special-case any form library. https://tanstack.com/query/latest/docs/framework/react/guides/mutations
5. **Composing the two**: RHF's `handleSubmit(onValid)` becomes the `<form onSubmit={...}>` handler, and inside `onValid(data)` you call `loginMutation.mutate(data)` (a `useMutation` whose `mutationFn` POSTs to the external API) — i.e. `<form onSubmit={handleSubmit(mutate)}>`. RHF drives client-side validation/UX (field errors), TanStack Query drives the network call (`isPending` to disable the submit button and prevent double submits, `onSuccess` to redirect/store tokens, `onError` to surface a server error banner). This exact composition is documented by the TanStack Query maintainer (TkDodo) in "React Query and Forms" — a high-credibility maintainer source, though not a page on tanstack.com or react-hook-form.com themselves. https://tkdodo.eu/blog/react-query-and-forms ; https://tanstack.com/query/latest/docs/framework/react/guides/mutations
6. Note: shadcn/ui's own current forms docs still show Zod usage in code but the doc's prose in one section said "Zod (v3 for schema validation)" — this may be stale relative to the Zod v4 stable release; given `@hookform/resolvers` explicitly supports Zod 4 (see version table), use **Zod v4** unless shadcn's docs are updated to say otherwise. https://ui.shadcn.com/docs/forms/react-hook-form ; https://github.com/react-hook-form/resolvers

## 5. Markdown pipeline tradeoff table

For a client component rendering **arbitrary markdown strings at runtime** (not build-time MDX compilation):

| Criterion | `react-markdown` + `remark-gfm` | `next-mdx-remote` | MDX runtime compile (`@mdx-js/mdx` `evaluate`) | `markdown-to-jsx` |
| --- | --- | --- | --- | --- |
| Runtime vs build-time | Fully runtime; parses markdown string to AST → React elements on every render (memoizable). | Two-phase: `serialize()` must run **server-side** (build time or a server request); `<MDXRemote>` then hydrates client-side from the pre-serialized payload. Not usable in a pure client-only/static-export app without a server step. https://github.com/hashicorp/next-mdx-remote | Runtime compile of MDX (which is JS) from an arbitrary string — explicitly a code-execution/RCE risk unless the string is trusted; not appropriate for arbitrary/user-supplied strings. (General MDX guidance, e.g. via Next.js MDX docs describing MDX compiling to executable JS.) | Fully runtime; component-per-tag override API, fewer deps than react-markdown. |
| Client-component fit | Good — pure JS parse + render, no server step needed. | Poor for this app: needs a server or build step for `serialize()`, which the static-export `tod-blog` app does not have. | Poor for arbitrary/untrusted strings (executes as code); fine only for known/trusted MDX. | Good — same runtime-only profile as react-markdown. |
| Bundle size / deps | Pulls in `unified`/`remark`/`rehype` stack (multiple small packages) — moderate. | Similar remark/rehype-based stack plus MDX compiler pulled in wherever `serialize()` runs. | Includes the MDX compiler at runtime — heavier, since compiling JSX-from-string at runtime is non-trivial. | markdown-to-jsx has fewer dependencies / a smaller footprint than react-markdown per package comparisons (3.8M weekly downloads vs react-markdown's 11.3M, per npm-compare/moiva aggregation — secondary source, not primary docs). |
| Plugin ecosystem | Large — full `remark`/`rehype` plugin ecosystem (`remark-gfm`, `remark-math`, `rehype-katex`, `rehype-slug`, `rehype-autolink-headings`, etc.) works directly. | Same remark/rehype plugin ecosystem, but gated behind the server-side `serialize()` step. | Same underlying MDX/remark/rehype pipeline, but oriented around compiling actual JSX, which is unnecessary complexity for plain markdown strings. | Smaller/self-contained plugin model (component overrides), not the remark/rehype ecosystem — GFM tables etc. need markdown-to-jsx's own options rather than remark plugins. |
| Maintenance status | Actively maintained: v10.1.0, 15.8k GitHub stars, per GitHub repo metadata fetched during this research. https://github.com/remarkjs/react-markdown | Actively maintained by HashiCorp; but architecturally mismatched to this app's static-export/client-only constraint. https://github.com/hashicorp/next-mdx-remote | Actively maintained as part of the MDX project, but wrong tool for "arbitrary string, no code execution" requirement. | Actively maintained; smaller community than react-markdown (2.3k stars vs react-markdown's ~15k per search-aggregated npm-compare data — secondary source). |

**Recommendation** (scope: GFM + syntax highlighting + copy button only — math/KaTeX and mermaid are explicitly deferred to future extensions via `remark-math`/`rehype-katex` and a mermaid rehype plugin, respectively): **`react-markdown` + `remark-gfm`**. It is the only option in this comparison that is (a) fully client-runtime-safe for arbitrary strings, (b) has no server-step dependency incompatible with `output: 'export'`, and (c) has the deepest, most current plugin ecosystem for GFM tables/footnotes/strikethrough/tasklists (all included in `remark-gfm`) and heading anchors via off-the-shelf `rehype-slug`/`rehype-autolink-headings`. `next-mdx-remote` is ruled out specifically because its `serialize()` step is documented as server-side-only, which conflicts with this app's static-export, client-only architecture. https://github.com/remarkjs/react-markdown ; https://github.com/hashicorp/next-mdx-remote

For syntax highlighting inside that pipeline: use **react-markdown v10's `MarkdownHooks` component**, which exists precisely to support async plugins like Shiki on the client (it renders via `useEffect`/`useState` and accepts a `fallback` prop while highlighting loads) — pair it with `@shikijs/rehype`. https://github.com/remarkjs/react-markdown ; https://shiki.style/packages/rehype. Shiki's own performance guide recommends fine-grained imports (`shiki/core` + `shiki/engine/javascript` + individual `@shikijs/langs`/`@shikijs/themes` modules, optionally generated by `shiki-codegen`) to avoid the default WASM/Oniguruma bundle in the browser; absent that tuning, Shiki's full/web bundles are heavy (reported ~700KB–1.2MB gzipped for broad language sets per secondary benchmarking), whereas Prism-based renderers (`prism-react-renderer`) stay lighter (~20KB core + per-language cost) at the cost of lower-fidelity theming — acceptable fallback if the tuned-Shiki bundle still proves too large. https://shiki.style/guide/best-performance (primary); bundle-size figures are secondary-source aggregation (pkgpulse.com, npm-compare.com) since no primary doc publishes exact gzip numbers for both libraries side by side.

For prose styling of the rendered output, two off-the-shelf options exist: `@tailwindcss/typography` (`prose` classes; Tailwind v4 supported per peerDeps) and shadcn's **`typeset`** system (July 2026) — one first-party CSS file styling headings/lists/tables/code blocks under `typeset typeset-docs` classes, with size/leading/flow controls and no dependency on @tailwindcss/typography. https://registry.npmjs.org/@tailwindcss/typography/latest ; https://ui.shadcn.com/docs/typeset

## 7. Open questions (not found / could not verify against a primary source)

- **Official Storybook monorepo/workspace placement guidance**: I could not find a first-party storybook.js.org doc that explicitly recommends (or discourages) a dedicated sibling `packages/ui-storybook`-style package versus colocating Storybook inside a component-library package. The material found (GitHub Discussions #22521, #11351) is community/maintainer discussion, not shipped documentation — not found as an authoritative, citable "official" recommendation either way.
- **Storybook + Tailwind v4-specific integration steps**: the official recipe at `storybook.js.org/recipes/tailwindcss` does not version-qualify its instructions for Tailwind v4 specifically (it assumes Vite auto-handles PostCSS and doesn't call out v4's `@import "tailwindcss"` / `@plugin` CSS-first config style) — not found as an explicit v4-specific walkthrough on storybook.js.org.
- **A canonical, official "react-hook-form + TanStack Query" combined recipe on either docs site**: neither react-hook-form.com nor tanstack.com publishes a joint doc page for a login/register flow. The pattern in section 4 is cited to the TanStack Query maintainer's blog (https://tkdodo.eu/blog/react-query-and-forms), which is high-credibility but not a first-party docs page — an official docs-site recipe was not found.
- **Whether Zod v4 is shadcn/ui's currently documented default**: `ui.shadcn.com/docs/forms/react-hook-form` content fetched during this research still read "zod (v3 for schema validation)" in places, which may be stale prose not yet updated for Zod 4's stable release — not confirmed which version shadcn's docs currently recommend by default as of 2026-07-13.
- **Base UI vs Radix for a new `packages/ui`**: as of July 2026 shadcn/ui defaults new projects to Base UI, with Radix available via `-b radix` (https://ui.shadcn.com/docs/changelog). Which base this repo should standardize on is a decision, not a research finding — most third-party examples/blocks in the wild still target the Radix-era components; no official migration-pressure statement found.
- **`rehype-katex` long-term maintenance risk** (future-extension concern only — math is out of current scope): confirmed no new npm release in the trailing 12 months (via Snyk advisor, a secondary source) but could not find an official statement from the `remarkjs/remark-math` maintainers about the project's maintenance status/roadmap — not found.
- **shadcn `typeset` Tailwind-v4-specific compatibility statement**: the typeset docs show it imported after Tailwind in CSS and it is dependency-free, but an explicit "works with Tailwind v4" compatibility line was not found on the page.
