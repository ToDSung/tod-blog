# specs/ 撰寫說明

`specs/` 放進行中與已完成的工作規格。一個主題一個資料夾（例如 `specs/ui-library/`），資料夾內固定兩份文件：`spec.md` 寫「要做什麼、為什麼」，`plan.md` 寫「怎麼做、誰做、做完怎麼驗」。範例照 `specs/ui-library/`。

文字風格依 [.agents/docs/writing-standards.md](../.agents/docs/writing-standards.md)。本檔只規定 spec 與 plan 的結構與硬規則。

## spec.md 的固定章節

1. 標題與狀態行：`Status: Draft v<n>（日期，一句話說明目前卡在哪或等誰）`。owner 核准後改成 `Approved`。
2. 目標與定位：這個東西要解決什麼問題、服務誰、長期方向如何影響設計優先序。
3. Decision Log：已定案的決策，見下方硬規則。
4. 技術棧與版本：套件、版本、備註。版本寫實測值，並註明實測日期與來源。
5. 架構：目錄結構、跨套件接線與約束。
6. 功能需求（FR）與非功能需求（NFR）：編號，一條一句。
7. 驗收標準：機械可查，見下方硬規則。
8. 範圍外：明確寫出這次不做什麼，以及未來復啟時該回頭讀哪一份研究。
9. 未決事項：實作時才能決定的事，定案後回寫本節。

## plan.md 的固定章節

1. 開頭指向對應的 `spec.md` 與派工規則文件。
2. 執行紀律：每個任務都適用的規則（測試門檻、commit 規則、審查方式）。
3. Phase 分節：每個 Phase 一張表，欄位為任務編號、任務、執行者、驗收。
4. 每個 Phase 最後一列是 `<n>.R` 審查任務：新 context 執行，只拿驗收標準與產出位置。
5. 里程碑與依賴：一張 ASCII 圖說明哪些 Phase 可以平行。

## 硬規則

驗收欄必須機械可查。可以貼成指令與預期輸出的才算數：`pnpm -F <pkg> test` 全綠、`npx eslint .` 無輸出、產出的 HTML 含某個字串。禁止「完成」「正常運作」「品質良好」這類無法判定真假的字眼。主觀項（視覺品質、觀感）要明寫由 owner 驗收，不由 agent 自評。

Decision Log 的列格式是「編號、決策、理由、日期」，編號用 `D1`、`D2` 依序遞增。文件只寫現況：決策被推翻或取消時，就地改寫該列的決策、理由與日期，不留原文、不用刪除線。編號一律不重排、不回收，因為 plan.md 與 commit 訊息會引用它。

未決事項定案後，把結論寫進它該去的地方（Decision Log、技術棧或架構章節），再把該條目從未決清單刪掉。清單清空就整節刪掉。

被評估過但不採用的方案，只有在「未來有人會再提一次」時才記，寫進「範圍外」底下的「已評估不採用」子節：一行一個方案，加一句純事實的不採用理由，最好是實測結果。不寫日期、不寫原決策全文、不寫心路歷程。判準是這一行能不能讓下一個 agent 少走一次冤枉路；不能就不要寫。

需要完整的決策沿革時查版本紀錄，例如 `git log -p --follow specs/<主題>/spec.md`。文件負責現況，git 負責歷史，兩邊不重複。

Phase 完成時在標題加 ✅ 與完成日期，底下用兩三行寫實際做了什麼與驗證結果。這是計畫表格裡唯一允許的圖示用法。

spec 與 plan 的分工界線：決策與理由只寫在 spec，工序與派工只寫在 plan。實作中改變決策時，先回寫 spec 的 Decision Log，再調整 plan 的任務；不要只改 plan，那會讓兩份文件對不上。

## 生命週期

草稿 → owner 核准 → 實作（每個 Phase 一個以上 commit）→ 實作發現的事實回寫 spec → 全部 Phase 完成後在狀態行標記完成日期。資料夾保留不刪，之後的工作要引用它。
